# Verification Signing Key Rotation (SUN-0500)

See [ADR 0033](../decisions/0033-ed25519-signer-and-key-registry.md) for the
full rationale. This document is the operational summary.

## Scope of this increment

SUN-0500 implements the `KeyRegistry` data structure and its rotation state
machine (`packages/verification/src/receipt/key-registry.ts`). It does **not**
implement production key custody, HSM/KMS integration, or an operational
rotation procedure against a live signing service — those remain future scope.
Every key exercised by SUN-0500's tests and fixtures is an ephemeral, in-memory,
`environment: 'test'` key generated by `generateTestKeypair()` and never
persisted.

## Key lifecycle

```
active → retiring → retired
   \-------------------> revoked
```

- **`active`**: the current signing key. New receipts may be issued with it;
  `canVerifyWith` returns `true`.
- **`retiring`**: still verifies; new issuance should move to a newer key (not
  enforced by `KeyRegistry` itself — that policy belongs to the issuer).
- **`retired`** (`registry.retire(keyId, retiredAtIso, replacementKeyId?)`):
  still verifies historical receipts signed while it was active — retiring a key
  must never invalidate receipts that were valid when issued.
- **`revoked`** (`registry.revoke(keyId)`): never verifies again, including
  receipts legitimately signed before revocation. Revocation is reserved for
  compromised keys, where every receipt signed with that key becomes suspect —
  this is the one state transition that is intentionally destructive to
  historical verifiability, and it should only be used when a private key is
  known or suspected to have leaked.

## Key IDs are never reused

`KeyRegistry.register` throws if `key_id` is already registered. Rotating a key
means generating a new key pair with a new `key_id` and registering it, never
overwriting an existing `key_id`'s public key material — a receipt's
`signing_key_id` must always resolve to the one public key that was live for
that identifier at signing time.

## Operational rotation procedure (future work)

Not implemented in SUN-0500: automated rotation scheduling, HSM/KMS-backed
private key storage, a rotation runbook against a live registry service, and
alerting on keys approaching a rotation deadline. Track as a follow-up increment
before any production signing key is issued.
