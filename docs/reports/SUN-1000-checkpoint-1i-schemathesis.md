## 2. Trivy classification normalization

The accepting message's argument is correct and is applied here as a disclosed
**taxonomy refinement**, not a claim that the original Checkpoint 1A text
already said this. Re-reading that text precisely
(`docs/reports/SUN-1000-security-release-gate-baseline.md`): its
FAIL_INTERNAL/BLOCKED_EXTERNAL distinction was drawn specifically around whether
a criterion's **tooling could even be installed and attempted locally** —
"missing local tooling/test suites" (FAIL_INTERNAL) versus "external services,
accounts, DNS, or infrastructure SITEBORNE does not already control locally"
(BLOCKED_EXTERNAL). Checkpoint 1H's finding is a case that 1A's original two-way
split did not anticipate: the tool is installed, executes successfully, and
produces a truthful, real result — but closing that result requires a third
party's (Traceloop's) future release, verified directly against the live npm
registry API (not a stale CLI cache) to have no currently-available compatible
version.

This fits the **intent** of `BLOCKED_EXTERNAL` — nothing further is achievable
through SITEBORNE's own engineering effort — far better than `FAIL_INTERNAL`'s
original "we simply haven't built/installed this yet" sense. Per the accepting
message's explicit instruction, this normalization is applied:

**Trivy: `FAIL_INTERNAL` → `BLOCKED_EXTERNAL`.**

The underlying security result is **unchanged and not weakened**: `CRITICAL=0`,
`HIGH=3` (all three
`@opentelemetry/{sdk-node, exporter-prometheus,propagator-jaeger}`, re-confirmed
unchanged this checkpoint), criterion still not `PASS`. This is bookkeeping
normalization only.

## 8. Execution architecture

Schemathesis (a separate Python process) needs a real, bindable HTTP socket —
this project's existing `app.request()` in-process test client only works within
the same Node process, so a real local server was required. A bare `tsx`/`node`
invocation of the full app import graph failed on two genuine, reproducible
environment issues (a top-level `await` in
`packages/verification/src/canonical.ts` incompatible with `tsx`'s default CJS
transform, then an ESM/CJS workspace-symlink interop failure even with ESM
forced) — this repository's workspace TS dependency graph only resolves cleanly
through Vitest's own transform pipeline (proven by 150+ passing test files), not
bare `tsx`/`node`. Rather than build a custom bundler pipeline to work around
this, `apps/edge-api/tests/schemathesis-server-host.test.ts` hosts the server
**inside a Vitest test file**, reusing exactly the tooling every other suite in
this repository already depends on. It is guarded by
`describe.skipIf(!isOrchestratorRun)` keyed on `SCHEMATHESIS_SERVER_HOST=true`
(only the orchestrator sets this) so it is safe to sit in the ordinary
`apps/edge-api/tests/` glob without ever affecting a normal
`pnpm test`/`pnpm check` run — verified directly: skipped in <1s when unset,
real 20s server session when set.

`@hono/node-server@2.1.1` (official Hono-team adapter, pinned exact version)
binds the already-proven `buildPaidServicesApp` Hono app to a real ephemeral
`127.0.0.1` port. `scripts/security/run-schemathesis.ts` orchestrates: spawn the
Vitest server host → poll a file-based ready-signal
(`.security-tools/schemathesis-server-ready.json`, bounded 30s timeout) → run
the pinned Schemathesis CLI against the real base URL → write a stop-sentinel
file → wait for clean shutdown (bounded 15s, force-kill fallback). Verified
manually end-to-end before wiring the full orchestrator: real 400 validation
response observed via `curl` against the live server.

`not_a_server_error`, `status_code_conformance`, `content_type_conformance`,

genuine security-boundary question. This is a disclosed, reasoned scope decision
for the first pass, not a silent weakening.

## 11. A discovered, disclosed `$ref`-naming defect — deliberately not fixed in the committed artifact

Schemathesis initially could not even load the schema: all 4 paid- service
operations' request/response `$ref`s point at component names
(`CompanyEvidenceGraphInput`, etc.) that do not exist anywhere in the document —
the real, registered names (`CompanyEvidenceInput`, etc.) are derived from each
schema file's on-disk base name, while the `$ref` names were separately derived
from each service ID's own slug; the two derivations disagree because
`company_evidence_graph` (service ID) doesn't literally match `company-evidence`
(schema file base). The same root cause also left every operation's `summary`
field reading literally `"Execute undefined service"` (`SERVICE_TITLES` lookup
used the same mismatched key).

A **correct, minimal generator fix** was written
(`packages/pcc-schema/scripts/generate-openapi.ts`: build the inverse of the
existing `SERVICE_IDS` mapping once, and derive every name from it so the two
can never disagree by construction), verified to produce exactly the intended
12-line diff with zero unrelated changes, and confirmed to resolve the
schema-loading failure completely — then **deliberately reverted**. Committing
it would change fields the repository's own `contracts:compat:check` gate
classifies as `required_version_bump: "major"` against the already-frozen
`contracts/releases/1.0.0` baseline (confirmed by direct execution: the same fix
triggers "12 incompatible changes, human_review_required" against that frozen
release). Bumping a frozen contract release is a separate governance decision
this Schemathesis-testing checkpoint has no authority to make unilaterally —
conflating the two would be exactly the kind of scope creep this checkpoint's
own directive warns against.

Instead, `run-schemathesis.ts` patches **only its own ephemeral, gitignored
copy** of the schema (`.security-tools/schemathesis-patched-schema.json`) via a
pure, unit-tested `patchKnownRefMismatches()` function before handing it to
Schemathesis — the committed artifact and the frozen baseline are both
completely untouched (`git diff` confirms zero changes to `packages/contracts/`,
`packages/pcc-schema/scripts/generate-openapi.ts`, or anything under
`contracts/releases/`).

## 12. Real campaign results

```
Operations: 4/4 selected and tested (quotes/{service_id} excluded, §5)
Test cases generated: 36
Unique failures: 12
Unexpected 5xx (not_a_server_error): 0
Execution duration: ~19s
Seed: 20260816
```

**12 findings, both root-caused to the same class of issue, fully triaged — not
homogenized without inspection:**

- **8 findings**: real `400` validation-error responses (confirmed via direct
  `curl` against the live server:
  `{"error": "invalid_request", "message": "...", "details": {...}}`) don't
  match the OpenAPI document's declared `400` response schema (the full
  canonical `StructuredError` envelope: `error_id`, `error_code`, `category`,
  `retryable`, `request_id`, `service_id`, `occurred_at`, ...).
- **4 findings**: real `402` Payment Required responses (the genuine x402
  protocol challenge shape: `x402_version`, `quote_id`, `requirement_id`, ...)
  likewise don't match the declared `StructuredError` schema.

**Classification: both `OPENAPI_DEFECT`, 0 `REAL_API_DEFECT`, 0
`TEST_HARNESS_DEFECT`, 0 `ENVIRONMENT_LIMITATION`.** The document describes the
wrong response schema for these two status codes on these four operations — a
real, genuine, understood documentation gap, not a security defect in the
running service (the API's actual behavior, already extensively covered by
SUN-0700A's own deep D1/x402 test suite, is not in question). **Not fixed this
checkpoint**, for the identical reason as §11: any correction to these declared
response schemas would touch the same frozen `contracts/releases/1.0.0` fields
and trigger the same major-version-bump governance question — this checkpoint's
own scope does not extend to that decision.

**Positive security signal**: zero `not_a_server_error` violations across the
full campaign — the API never returned an unexpected 5xx for any
schema-valid-or-invalid generated input across 36 cases.
